## 4. 启动链（这块板最关键的部分）

```
                     ┌──────────────────────────────────────────────┐
 ① BootROM (片内)    │ 扫描 FSPI → eMMC → SDMMC(TF) → USB            │
                     │ 原厂 eMMC 有有效 loader，因此 SPL 从 eMMC 加载 │
                     └───────────────────┬──────────────────────────┘
                                         ▼
 ② DDR init + SPL    │ U-Boot SPL 2017.09 (fwver v1.13)              │
   （来自 eMMC       │ ★ 日志 L35 "Trying to boot from MMC2" (TF卡)  │
     sector 64）     │ ★ 日志 L36 "MMC: no card present" → L39 L40   │
                     │   "Trying to boot from MMC1" (eMMC)           │
                     │ → **插上带 FIT 的 TF 卡时，SPL 会先从卡加载** │
                     └───────────────────┬──────────────────────────┘
                                         ▼
 ③ FIT @ sector 0x4000 (=16384)
                     │ atf-1 / uboot / fdt / atf-2 / atf-3 / optee   │
                     │ 日志 L41–L49，`## Verified-boot: 0`（不验签）  │
                     └───────────────────┬──────────────────────────┘
                                         ▼
 ④ BL31 v2.3 (v1.45) + OP-TEE 3.13 (v1.16) → U-Boot proper 2017.09
                     │ mmc@fe2c0000: 1 (TF) , mmc@fe2e0000: 0 (eMMC)│
                     │ ★ boot_targets = usb0 mmc1 mmc0 mtd2 ...      │
                     │   → distro boot 也是 TF(mmc1) 优先于 eMMC(mmc0)│
                     │ boot_scripts = boot.scr.uimg boot.scr          │
                     │ boot_prefixes = / /boot/                       │
                     └───────────────────┬──────────────────────────┘
                                         ▼
 ⑤ /boot/boot.scr → 读 armbianEnv.txt → load Image / uInitrd / dtb → booti
```

### 4.1 为什么"不擦 eMMC 也能 TF 卡启动"

有两层保障，且都在**这块板的实测日志/固件二进制**里得到确认：

1. **SPL 层**：BootROM 虽然优先 eMMC，但 eMMC 上的 SPL 在找下一阶段 FIT 时
   **把 MMC2（TF 卡）排在 MMC1（eMMC）前面**（日志 L35–L40）。
   只要 TF 卡 sector 16384 上有合法 `u-boot.itb`，U-Boot 就从卡上起来。
2. **U-Boot 层**：内嵌环境 `boot_targets=usb0 mmc1 mmc0 mtd2 mtd1 mtd0 pxe dhcp`，
   `mmc1` = TF 卡在前，distro boot 会先扫卡上的 `/boot/boot.scr` 与
   `/boot/extlinux/extlinux.conf`，命中后不再回落到 eMMC。

> 这一结论与 ophub 为 `ALIENTEK-QuarkPi-CA2` 做的特殊处理
> （同时发布 `mmc0_extlinux/extlinux.conf` 与 `mmc1_extlinux/extlinux.conf`）是同一个成因；
> 本工程把这套双保险也加上。

### 4.2 BootROM 优先级的兜底策略

如果个别批次板子 BootROM 固化成"eMMC 绝对优先、SPL 不扫 SD"，
用 `scripts/04-android-emmc-guard.sh` 在**板内**把 eMMC 的
sector 64..32767（bootloader 区，16 MiB − 32 KiB）**先备份再清零**：
GPT 表头在 LBA 1–33，不受影响；Android 所有分区数据完好，
写回备份即可完整恢复原厂系统。此为可逆操作，脚本强制先备份。

## 5. 基础镜像的启动布局（离线实测）

| 偏移 | 内容 | 实测 |
|---|---|---|
| LBA 0 | protective MBR（全 0，GPT 保护头） | `00...` |
| LBA 1 | GPT header `EFI PART`，first usable LBA 2048 | ✅ |
| LBA 2–33 | GPT 分区项：`p1 rootfs`，**start=32768（16 MiB）**，end=20928511，10203 MiB | ✅ |
| sector **64** (0x8000) | `RKNS` idbloader（TPL/SPL + DDR 固件），有效数据 335872 B | ✅ |
| sector **16384** (0x800000) | `u-boot.itb` FIT（`FIT Image with ATF/OP-TEE/U-Boot/MCU`），有效数据 1642496 B | ✅ |
| **16 MiB** | ext4 rootfs（`label=armbi_root`, `UUID=472439f3-fc43-4c91-8d3b-ed3299b3defe`, 4K block） | ✅ |

这正好符合 ophub `rebuild` 对 Rockchip 的定义：
`skip_mb=16` / `partition_table_type=gpt` / `dd ... seek=64` / `dd ... seek=16384`。

`/boot` 实测内容：

```
Image -> vmlinuz-6.1.115-vendor-rk35xx      uInitrd -> uInitrd-6.1.115-vendor-rk35xx
dtb   -> dtb-6.1.115-vendor-rk35xx/         (rockchip/ 下 466 个 dtb)
boot.cmd (4077 B)  boot.scr (4149 B)  armbianEnv.txt (188 B)
config / System.map / vmlinuz / initrd.img / uInitrd 均为 6.1.115-vendor-rk35xx
```

`/boot/armbianEnv.txt` 原文：

```
verbosity=1
bootlogo=true
console=both
extraargs=cma=256M
overlay_prefix=rockchip-rk3588
fdtfile=rockchip/rk3588-evb7.dtb          ← ❌ 该文件不存在
rootdev=UUID=472439f3-fc43-4c91-8d3b-ed3299b3defe
rootfstype=ext4
```

`/boot/boot.cmd` 关键行（证明它对本板其实是正确的）：

```
setenv rootdev "/dev/mmcblk0p1"                         # 被 armbianEnv.txt 的 UUID 覆盖
if test -e ... ${prefix}armbianEnv.txt; then ... env import -t ...   # 从当前设备读
setenv bootargs "root=${rootdev} ... console=ttyS2,1500000 ..."
load ${devtype} ${devnum}:${distro_bootpart} ${ramdisk_addr_r} ${prefix}uInitrd
load ${devtype} ${devnum}:${distro_bootpart} ${kernel_addr_r} ${prefix}Image
load ${devtype} ${devnum}:${distro_bootpart} ${fdt_addr_r} ${prefix}dtb/${fdtfile}   # ← 在这里失败
booti ${kernel_addr_r} ${ramdisk_addr_r} ${fdt_addr_r}
```

> **结论 3（根因）**：唯一的硬故障是 `fdtfile` 指向了不存在的
> `rk3588-evb7.dtb`，导致 `load ... /boot/dtb/rockchip/rk3588-evb7.dtb` 失败，
> 后续 `fdt addr` / `booti` 拿到空 dtb，系统卡在 U-Boot。
> 修正为 `rk3588-evb7-lp4-v10-linux.dtb` 即可，其余启动链路无需改动。

## 6. DTB 变体选择

`/boot/dtb/rockchip/` 下与本板相关的 7 份：

| DTB | 用途 | 是否选用 |
|---|---|---|
| `rk3588-evb7-lp4-v10-linux.dtb` | **V10 + LPDDR4 + Linux**，chosen 无 `androidboot.*` | ✅ **选用** |
| `rk3588-evb7-lp4-v10.dtb` | V10 + LPDDR4 + **Android**（chosen 带 `storagemedia=emmc` / `androidboot.*`） | ❌ |
| `rk3588-evb7-lp4-v10-rk1608-ipc-8x-linux.dtb` | V10 + 8 路 IPC 摄像头 | ❌ |
| `rk3588-evb7-v11*.dtb`（3 份） | **V11** 板型，与本板 V10 不符 | ❌ |
| `rk3588-evb7-lp4-v11-linux-ipc.dtb` | V11 板型 | ❌ |
| `rk3568-evb7-ddr4-v10.dtb` | RK3568，不同 SoC | ❌ |

两份 V10 DTB 都已抽取到 `assets/dtb/`，均包含 `rockchip,rk3588-evb7-lp4-v10`、
`rk3588-dw-mshc`、`vccio_sd_s0`、`rgmii-rxid`、`rk806`、`rk8602`、`ap6398s`、
`wlan-platdata`，确认与反编译 DTS 是同一套硬件描述。

## 7. 约束与风险清单

| # | 风险 | 应对 |
|---|---|---|
| R1 | BootROM 某些批次可能 eMMC 绝对优先 | `04-android-emmc-guard.sh` 可逆禁用 eMMC loader |
| R2 | 混用 ophub 主线 rk3588 内核 → rk806 / gmac / sdmmc 驱动全丢 | 固定使用 vendor 6.1.115 BSP 内核与 DTB |
| R3 | `root=/dev/mmcblk0p1` 在 TF/eMMC 双存在时设备号可能漂移 | `armbianEnv.txt` 已用 `root=UUID=...`（实测与 ext4 s_uuid 一致），保持不动 |
| R4 | Android eMMC 上 21 个 GPT 分区，误擦会毁原厂系统 | 所有 eMMC 操作强制"先备份 16 MiB、再验证备份、最后才写" |
| R5 | TF 卡 UHS SDR104 对卡品质敏感，坏卡会卡在 `mmc_init` | 用 A1/A2 级卡；失败时降速（`max-frequency` 降到 50 MHz 的 overlay） |
| R6 | AP6398S firmware 缺失导致无 WiFi | 首次启动后 `apt install firmware-brcm80211` 或从 Android `/vendor/firmware` 拷贝 |
| R7 | 白板专用 ICM42607 / NXPNFC / ebsw_pwm 在 Linux 下无驱动，i2c 报错刷屏 | 可选 DT overlay 关闭（见 `02-构建与刷写指南.md` §6） |
